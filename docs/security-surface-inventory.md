## Policy vocabulary

| Term | Executable meaning |
| --- | --- |
| Public | No session is required. Tenant context, when needed, is resolved from an opaque public ID, slug, or signed/random token rather than caller input. |
| Member | `requireOrgMember`: owner, admin, member, and viewer may proceed. |
| Writer | `requireOrgWriter`: owner, admin, and member may proceed; viewer receives `403`. |
| Admin | `requireOrgAdmin`: owner and admin may proceed; member/viewer receive `403`. |
| Session tenant | The handler passes the organization ID from the server-side session. Resource services must include it in SQL predicates; callers cannot select an organization ID. |
| Token tenant | A public identifier or token resolves the organization/resource in the service. Invalid or cross-resource tokens do not expose tenant data. |
| Browser CORS | Credentialed cross-origin browser traffic is reflected only for configured exact origins. Unsafe requests still pass the CSRF/origin boundary; allowed request headers are `Content-Type`, `Authorization`, and the non-secret `Idempotency-Key` used by portable-export requests. |
| Hosted write policy | Only a runtime configured with Stripe is managed. Every registered private managed-tenant mutation is classified from its exact method/route and enforces subscription writability after authentication and its normal role check. Canceled, expired-trial, unpaid, paused, incomplete, and incomplete-expired tenants receive `402`; unreadable configured policy receives `503`. Reads/exports, workspace offboarding export requests, billing recovery, durable-job replay, own profile/preferences, notification acknowledgement, invitation revocation, public compliance/provider callbacks, and the Stripe webhook are explicit exceptions. Invitation resend remains a normal managed write. Public lead capture and replayed non-billing work use the same managed boundary. Fake/self-hosted mode reports `unmanaged`, exposes unlimited local usage, and skips hosted lifecycle/limit checks across private routes, public leads, and workers so stale hosted fields cannot restrict core data. |
| Plan create | The route checks both subscription writability and the named seat/record limit. Configured limit reads fail closed; a nil billing service remains compatible with isolated tests/callers. Current named resources are seats, contacts, and deals. |
| Request telemetry | Request ID and structured completion logs plus bounded-route Prometheus counters/histograms are emitted by global middleware. Metrics never label tenants, record IDs, addresses, or request bodies. |
| Shared public abuse budget | A static route scope and one-way SHA-256 client digest identify an atomic PostgreSQL fixed window; no raw address is retained. All API processes consume the same bounded counter, return the remaining window in `Retry-After`, and fail closed with `503 RATE_LIMIT_UNAVAILABLE` when enforcement cannot be verified. Expired rows are removed in bounded opportunistic batches. |

Unless a row says otherwise, private routes have no endpoint-specific rate limit; they rely on the authenticated session, the cross-cutting hosted write policy for tenant mutations, CSRF/origin checks for unsafe methods, the 1 MiB JSON body limit (2 MiB import upload), server timeouts, and global request telemetry. The policy registration test sends every classified route through an inactive tenant and fails if any route misses the authorization/billing boundary. This is a map of current behavior, not a claim that every control is sufficient.

## Findings that constrain maturity claims

- Authentication and role helpers are consistent, but explicit forbidden-role and cross-tenant handler tests are concentrated in the core CRM. Newer Part II foundations need a systematic negative-path matrix before promotion.
- Hosted lifecycle enforcement is centralized across the current private route set, public lead writes, non-billing tenant workers, and persistent role-aware frontend controls. A credential-free Stripe HTTP/PostgreSQL contract journey now covers the app boundary, and a retained source-reconciled usage view covers seats, active records, sent email, successful automation/jobs, and estimated tenant row bytes. The hosted catalog exposes enforced capacity but deliberately grants no unapproved features; the UI does not present incomplete API/SSO/automation/reporting outcomes or hard-coded price hints as Stripe promises. Existing seat/contact/deal capacities are concurrency-safe: a short-lived tenant/resource claim is counted with committed usage, and the effect transaction holds the tenant lock while deleting the claim, so another request observes either side of the atomic handoff. All direct, import, public lead, reactivation, and archive-recovery paths use that contract; the internal claim ledger is excluded from exports and storage billing evidence. Hosted SaaS remains a foundation because feature policy and broader period-meter quotas are not approved/enforced, API usage has no external API surface to measure, dunning/proration/resubscription and retention policy remain undecided, and credentialed Stripe test-mode acceptance has not been approved/run.
- Private endpoints have no per-tenant/session request budget. Public limits coordinate through PostgreSQL across processes and restarts, but they are application controls rather than a volumetric DDoS boundary. Add an approved production edge/WAF plus bot and consent controls to lead submission before promoting public lead generation beyond foundation maturity.
- Global logs provide request correlation; protected time-series request/database/provider/job/notification/backup metrics and reference alert rules now exist. Production scrape credentials, an alert destination, redaction verification, SLO validation, and telemetry-store retention policies remain operator/pilot work.
- Sensitive writes are not uniformly represented in audit events. Each converged feature slice must add audit coverage before its maturity is promoted.
- The route guard detects any route-set change, but it does not prove service SQL isolation. Database integration and explicit cross-tenant/forbidden-path tests remain required for each promoted capability.

## Maintenance rule

When adding, removing, or renaming a route or background operation:

1. Review all seven dimensions in this inventory before changing the expected count/digest.
2. Add proportional unauthenticated, forbidden-role, cross-tenant, entitlement, rate-limit, and failure-path tests.
3. Update the capability matrix and runbook if the route changes an exposed outcome or operator workflow.
4. Recompute the sorted registration digest only after review; never update the guard solely to make the test pass.
